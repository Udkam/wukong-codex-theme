# 开发与打包

## 运行源码

Windows 上双击根目录 start.cmd。实际启动由 scripts/start.ps1 处理，定位官方包并使用其嵌入式 Node；普通用户不需要 npm。

## 验证

### 新 UI 适配后的旧方案清理

完成新 UI 修改与适配后，必须删除已被替代的旧方案专用测试、断言和文案，包括过时的布局基准、版本描述、效果说明及验收结论。当前测试和文档只描述现行方案；旧方案的具体实现与恢复方法从 Git 历史和历史记录查找，不在现役目录保留并行的旧方案说明。

清理前应逐项区分“旧方案已失效”与“仍适用的功能或回归保护”：仍适用的保护应迁移到新 UI 的真实结构，不能通过删除失败测试掩盖缺陷。未进入版本历史的独有材料需先保留可恢复记录，再清理。

开发环境使用 Node.js 与 npm：

```powershell
npm ci
npm run check
npm run test:e2e
```

部分原生客户端合同要求 Windows 和匹配的已安装官方版本。测试通过不代表用户视觉验收；见 VALIDATION.md。

## 生成用户下载目录

目的目录必须不存在，且位于源码目录之外：

```powershell
node scripts/package-runtime.mjs --source . --destination ../Wukong-Codex-Theme
```

默认输出 start.cmd、使用说明.txt、app 三项。app 内仅复制活动清单引用的资源与必要运行文件。打包完成后将整个 Wukong-Codex-Theme 文件夹压缩为 ZIP；解压必须保留此结构。

内部测试需要平铺运行布局时，可显式增加 --layout runtime。这不是第二个面向用户的启动入口。

只构建目录不代表已经发布；上传 Release、设置版本及变更记录需单独执行。不要将 Source code 压缩包当作简化运行包。

## 源码与本地材料

宠物文件和历史截图保留本地但已取消跟踪。测试需使用索引导出的独立源码验证，避免本地材料遮盖缺失依赖。现役测试依赖的 V23/V24/V30/V31 证据暂保留，其他旧截图不作为当前效果证明。

## 查找旧方案

使用 `git log --all -- <路径>` 定位历史，再用 `git show <提交>:<路径>` 只读查看。此次适配前的基点为 `3a7ba65`。恢复旧文件应在独立目录进行，不覆盖当前方案。

## 固定更新与发布流程

自 v0.17.0 起，每次更新均按以下顺序完成：

1. 核对安装客户端原生代码和版本，整理问题、设计绘制范围，保留原生几何。
2. 实施修改并注入本机；执行定向及独立源码回归，记录实际页面、深浅模式和响应式检查。
3. 删除失效旧方案测试与文案，迁移仍有效的保护；历史恢复使用 Git。
4. **同步 README、当前版本链接、最新预览图、验证记录与发行说明**。预览必须来自本版真实界面，注明脱敏或夹具来源，不复用旧 UI 冒充当前效果。
5. 交用户实机验收；已有明确发布授权时继续执行，不重复请求同一确认。
6. 同步 package.json 与 package-lock.json 版本，从精确发布输入导出独立源码；构建下载包、解压比对哈希，排除本机诊断和无关材料。
7. 记录冷启动、恢复原生是否实际执行；未执行的项目不得写成通过。
8. 提交源码、推送对应提交与标签，创建 GitHub Release，上传 ZIP 与 SHA256SUMS.txt；回读 Release、下载链接、版本及哈希。
9. 更新当前版本文档，保留本机证据并释放临时调试资源。

该流程同时适用于后续 UI 适配与普通主题更新。用户对本轮发布的明确指示优先，禁止仅更新代码而遗留旧 README 或预览图。
